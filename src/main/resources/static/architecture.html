System Architecture Blueprint

Multi-tier modular architecture designed for zero capacity leakage, lock fairness, and build-time OpenAPI contract generation.

1. Client / Presentation Tier

  • Single Page Dashboard (HTML5, CSS3, ES6 Fetch)
  • RESTful HTTP clients & SDK consumers
  • Automated JUnit 5 & BDD Test Runners

2. API Controller Tier

  • WaitlistApiController implements WaitlistApi
  • Generated by openapi-generator-maven-plugin
  • RFC 7807 ProblemDetail error handling
  • Virtual Thread request dispatcher per connection

3. Core Domain Service

  • CourseWaitlistService (Thread-Safe)
  • ReentrantLock(true) fair queue serialization
  • Atomic enrollment, drop, and promotion evaluation
  • Skip-and-Retain waitlist tenure preservation

4. In-Memory Aggregate State

  • CourseOffering (ID, capacity, prerequisites)
  • enrolled: Bounded List<String> ($0 \le N \le \text{cap}$)
  • waitlist: FIFO List<String> queue
  • learners: ConcurrentHashMap<String, Learner>

Enrollment Workflow Sequence

Demonstrates how direct enrollments, waitlist placements, duplicate attempts, and prerequisite rejections are evaluated under fair lock serialization.

sequenceDiagram
    autonumber
    actor Client as Learner / Client
    participant Controller as WaitlistApiController
    participant Service as CourseWaitlistService
    participant Lock as ReentrantLock(true)
    participant Roster as Enrolled Roster
    participant Waitlist as FIFO Waitlist

    Client->>Controller: POST /api/enroll { learnerId: "alice" }
    Controller->>Service: enroll("alice")
    Service->>Lock: lock()
    Note over Service,Lock: Atomic Critical Section: FIFO Acquisition

    alt Learner Not Registered
        Service-->>Controller: EnrollmentResult(INVALID_REQUEST, "Not registered")
    else Already Enrolled
        Service-->>Controller: EnrollmentResult(ALREADY_ENROLLED, "Already enrolled")
    else Already on Waitlist
        Service-->>Controller: EnrollmentResult(ALREADY_WAITLISTED, "Already waitlisted")
    else Prerequisite Missing (e.g. Needs CS101)
        Service-->>Controller: EnrollmentResult(PREREQUISITE_NOT_MET, "Prerequisites not met")
    else Capacity Available (enrolled.size < capacity)
        Service->>Roster: add("alice")
        Service-->>Controller: EnrollmentResult(ENROLLED, "Enrolled successfully")
    else Course Full (enrolled.size == capacity)
        Service->>Waitlist: add("alice")
        Service-->>Controller: EnrollmentResult(WAITLISTED, "Waitlist position: N")
    end

    Service->>Lock: unlock()
    Controller-->>Client: 200 OK (EnrollmentResult JSON)

Drop & Skip-and-Retain Promotion Sequence

Details the atomic vacancy creation and waitlist scan, ensuring ineligible candidates retain queue seniority while promoting the earliest eligible learner.

sequenceDiagram
    autonumber
    actor Client as Dropping Student
    participant Controller as WaitlistApiController
    participant Service as CourseWaitlistService
    participant Lock as ReentrantLock(true)
    participant Roster as Enrolled Roster
    participant Waitlist as FIFO Waitlist

    Client->>Controller: POST /api/drop { learnerId: "alice" }
    Controller->>Service: drop("alice")
    Service->>Lock: lock()
    Note over Service,Lock: Atomic Critical Section: Vacancy & Promotion

    alt Learner In Waitlist
        Service->>Waitlist: remove("alice")
        Service-->>Controller: DropResult(DROPPED_FROM_WAITLIST)
    else Learner Not Enrolled
        Service-->>Controller: DropResult(NOT_ENROLLED)
    else Learner Enrolled (Seat Opened)
        Service->>Roster: remove("alice")
        Note over Service: 1 Seat Opened. Scanning Waitlist in FIFO Order...

        alt Waitlist Empty
            Service-->>Controller: DropResult(DROPPED, seatOpened=true)
        else Waitlist Has Candidates
            loop FIFO Queue Traversal (Index 0 to N-1)
                Service->>Waitlist: checkPrerequisites(candidate)
                alt Candidate Ineligible (Missing CS101)
                    Note over Service,Waitlist: SKIP & RETAIN: Kept at current queue position!
                else Candidate Eligible
                    Service->>Waitlist: remove(candidate)
                    Service->>Roster: add(candidate)
                    Note over Service: Earliest Eligible Candidate Promoted
                    Service-->>Controller: DropResult(DROPPED_AND_PROMOTED, candidateId)
                end
            end
            opt All Waitlist Candidates Ineligible
                Service-->>Controller: DropResult(DROPPED, seatOpened=true)
            end
        end
    end

    Service->>Lock: unlock()
    Controller-->>Client: 200 OK (DropResult JSON)

System Invariants & Mathematical Guarantees

The service strictly enforces four core invariants under all operating conditions and race events.

Invariant Formal Definition Enforcement Mechanism Test Verification
1. Capacity Invariant 0 ≤ |enrolled| ≤ capacity Checked inside fair lock before every enrollment and promotion operation. CourseEnrollmentTest, CourseConcurrencyTest
2. Mutual Exclusion enrolled ∩ waitlist = ∅ Idempotency guards check both collections before state mutation. CourseWaitlistTest, CourseDropsTest
3. Queue Seniority FIFO Arrival Order Appended to tail of waitlist; duplicate calls return ALREADY_WAITLISTED without resetting position. CourseWaitlistTest, BDD @waitlist
4. Prerequisite Invariant prerequisites ⊆ completedCourses Enforced during direct enrollment and evaluated at drop promotion time. CoursePromotionTest, BDD @promotion
